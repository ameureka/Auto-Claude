# Skill 内容编写标准

## 概述

本文档定义 Claude Code Skills 内容编写的标准和最佳实践，确保所有 Skills 的内容清晰、准确、可执行。

## 写作原则

### 1. 清晰性 (Clarity)

**目标**: 让读者一次就能理解

**要求**:
- 使用简单、直接的语言
- 避免行话和缩写（或在首次使用时解释）
- 一个句子表达一个想法
- 使用主动语态

✅ **好的示例**:
```markdown
运行以下命令构建项目：
```bash
npm run build
```
```

❌ **不好的示例**:
```markdown
项目构建可以通过执行相应的 npm 脚本来完成，该脚本会调用构建工具。
```

### 2. 精确性 (Precision)

**目标**: 提供准确、具体的信息

**要求**:
- 使用具体的数字和度量
- 避免模糊词汇（"快速"、"通常"、"可能"）
- 提供确切的命令和参数
- 明确前提条件和预期结果

✅ **好的示例**:
```markdown
等待 30 秒让服务完全启动
```

❌ **不好的示例**:
```markdown
等待一会儿让服务启动
```

### 3. 可执行性 (Actionability)

**目标**: 读者可以直接按照文档执行

**要求**:
- 每个步骤都是具体的操作
- 提供完整的命令（可直接复制粘贴）
- 说明每个步骤的预期结果
- 包含验证方法

✅ **好的示例**:
```markdown
1. 检查 Node.js 版本
   ```bash
   node --version
   ```
   预期输出: `v18.0.0` 或更高版本
```

❌ **不好的示例**:
```markdown
确保 Node.js 版本正确
```

### 4. 完整性 (Completeness)

**目标**: 包含所有必要的信息

**要求**:
- 说明前提条件
- 包含所有必需步骤
- 提供错误处理方法
- 包含验证和检查

### 5. 一致性 (Consistency)

**目标**: 整个文档使用统一的风格和术语

**要求**:
- 术语使用一致
- 格式风格统一
- 命名规范一致
- 结构模式一致

## 语言规范

### 语态和时态

**使用祈使句**（命令式）:
- ✅ "运行测试"
- ✅ "检查配置文件"
- ❌ "你应该运行测试"
- ❌ "我们需要检查配置文件"

**使用现在时**:
- ✅ "命令返回版本号"
- ❌ "命令将会返回版本号"

**使用主动语态**:
- ✅ "系统生成报告"
- ❌ "报告被系统生成"

### 词汇选择

#### ✅ 推荐使用

| 词汇 | 用途 | 示例 |
|------|------|------|
| 必须 (MUST) | 强制要求 | "必须运行测试" |
| 应该 (SHOULD) | 强烈建议 | "应该添加注释" |
| 可以 (MAY) | 可选操作 | "可以跳过此步骤" |
| 确保 | 验证要求 | "确保文件存在" |
| 验证 | 检查结果 | "验证输出正确" |

#### ❌ 避免使用

| 词汇 | 原因 | 替代词 |
|------|------|--------|
| 快速、迅速 | 模糊不清 | 具体时间（如"30秒内"） |
| 通常、一般 | 不确定 | 明确说明条件 |
| 可能、也许 | 不明确 | 明确说明或提供条件 |
| 简单、容易 | 主观判断 | 删除或说明具体步骤 |
| 很多、一些 | 不精确 | 具体数量 |

### 术语一致性

**建立术语表**:

在文档开头或 Quick Reference 中定义关键术语：

```markdown
## 术语说明

- **工作目录**: 项目的根目录，包含 `package.json` 文件
- **构建产物**: `npm run build` 生成的文件，位于 `dist/` 目录
- **测试套件**: 所有 `*.test.js` 文件中定义的测试用例
```

**保持一致**:
- ✅ 全文使用"工作目录"
- ❌ 混用"工作目录"、"项目目录"、"根目录"

## 格式规范

### 标题层级

使用清晰的标题层级结构：

```markdown
# Skill 标题 (H1 - 仅用于主标题)

## 主要章节 (H2 - 如 Quick Reference, Standard Workflow)

### 子章节 (H3 - 如工作流中的阶段)

#### 详细说明 (H4 - 如特定步骤的详细说明)
```

**规则**:
- 不要跳过层级（如从 H2 直接到 H4）
- 每个层级至少有 2 个项目（如果只有 1 个，考虑合并到上级）
- 标题简洁明了（5-8 个字为佳）

### 列表格式

#### 有序列表（步骤）

用于需要按顺序执行的步骤：

```markdown
1. **第一步标题**

   详细说明第一步的内容

   ```bash
   command-here
   ```

   预期结果: 描述预期输出

2. **第二步标题**

   详细说明第二步的内容
```

**规则**:
- 使用粗体标题
- 步骤之间空一行
- 包含命令和预期结果
- 最多两级嵌套

#### 无序列表（选项）

用于不分先后的项目：

```markdown
- **选项 A**: 说明
- **选项 B**: 说明
- **选项 C**: 说明
```

#### 检查清单

用于验证和检查：

```markdown
- [ ] 检查项 1
  - 验证方法
  - 预期结果

- [ ] 检查项 2
  - 验证方法
  - 预期结果
```

### 代码块格式

#### 命令行代码

使用 bash 语法高亮：

```markdown
```bash
# 注释说明命令的作用
npm run build

# 多个命令可以分组
npm test
npm run lint
```
```

#### 配置文件

使用对应的语法高亮：

```markdown
```json
{
  "name": "project-name",
  "version": "1.0.0"
}
```

```yaml
name: skill-name
description: Brief description
```
```

#### 输出示例

使用 text 或不指定语言：

```markdown
```text
✓ All tests passed
✓ Build completed successfully
```
```

### 强调和标注

#### 粗体

用于关键术语和步骤标题：

```markdown
**重要**: 这是关键信息
```

#### 斜体

用于变量和占位符：

```markdown
将 *your-branch-name* 替换为实际分支名
```

#### 代码标记

用于内联命令、文件名、变量：

```markdown
运行 `npm install` 安装依赖
编辑 `package.json` 文件
设置 `NODE_ENV` 环境变量
```

#### 引用块

用于重要提示和警告：

```markdown
> **注意**: 此操作不可逆，请谨慎执行

> **提示**: 可以使用 `--dry-run` 参数预览结果
```

### 表格格式

用于对比和参考信息：

```markdown
| 参数 | 类型 | 必需 | 说明 |
|------|------|------|------|
| `--version` | string | ✅ | 版本号 |
| `--tag` | string | ❌ | Git 标签 |
```

**规则**:
- 表头清晰
- 列宽适中
- 使用 ✅ ❌ 等符号增强可读性
- 对齐方式一致

## 内容组织

### Quick Reference 编写

**目的**: 让用户 30 秒内了解核心内容

**结构**:
```markdown
## Quick Reference

**一句话说明**: 这个 Skill 做什么

**核心命令**:
- `command-1` - 说明
- `command-2` - 说明

**关键文件**:
- `file-1` - 说明
- `file-2` - 说明

**快速检查**:
- [ ] 检查项 1
- [ ] 检查项 2
```

**要点**:
- 不超过 20 行
- 只包含最常用的信息
- 使用简洁的语言
- 提供快速检查清单

### Standard Workflow 编写

**目的**: 提供清晰的操作步骤

**结构**:
```markdown
## Standard Workflow

### 准备阶段

1. **检查前提条件**

   说明需要满足的条件

   ```bash
   verification-command
   ```

   预期: 描述预期结果

2. **准备环境**

   说明准备步骤

### 执行阶段

3. **执行主要操作**

   详细说明

4. **验证结果**

   说明如何验证

### 完成阶段

5. **清理和收尾**

   说明收尾工作
```

**要点**:
- 使用阶段分组（准备、执行、验证、完成）
- 每个步骤包含：标题、说明、命令、预期结果
- 步骤编号连续
- 包含验证步骤

### Common Scenarios 编写

**目的**: 提供实际使用案例

**结构**:
```markdown
## Common Scenarios

### 场景 1: [场景名称]

**背景**: 描述使用场景和背景

**前提条件**:
- 条件 1
- 条件 2

**步骤**:
1. 步骤 1
2. 步骤 2
3. 步骤 3

**预期结果**: 描述完成后的状态

**注意事项**:
- 注意点 1
- 注意点 2

---

### 场景 2: [场景名称]

[同样的结构]
```

**要点**:
- 3-5 个典型场景
- 每个场景独立完整
- 包含背景、步骤、结果
- 使用分隔线分隔场景

### Critical Rules 编写

**目的**: 明确必须遵守和必须避免的规则

**结构**:
```markdown
## Critical Rules

### ✅ ALWAYS

1. **ALWAYS [规则描述]**
   - **原因**: 为什么必须这样做
   - **方法**: 如何执行
   - **示例**: 具体示例

2. **ALWAYS [规则描述]**
   [同样的结构]

### ❌ NEVER

1. **NEVER [规则描述]**
   - **原因**: 为什么不能这样做
   - **后果**: 违反的后果
   - **替代**: 正确的做法

2. **NEVER [规则描述]**
   [同样的结构]
```

**要点**:
- 3-7 条核心规则
- 每条规则说明原因
- 提供具体示例
- ALWAYS 和 NEVER 分开

### Verification Checklist 编写

**目的**: 提供可执行的验证步骤

**结构**:
```markdown
## Verification Checklist

### [分类 1]

- [ ] **检查项 1**
  ```bash
  verification-command
  ```
  预期: 描述预期结果

- [ ] **检查项 2**
  - 验证方法
  - 预期结果

### [分类 2]

- [ ] **检查项 3**
  [同样的结构]
```

**要点**:
- 按类别分组（如代码质量、版本管理、发布准备）
- 每项可独立验证
- 提供验证命令或方法
- 说明预期结果
- 5-10 个检查项

## 示例和代码

### 命令示例

**完整性**:
```markdown
✅ 好的示例:
```bash
# 安装依赖
npm install

# 运行测试
npm test

# 构建项目
npm run build
```

❌ 不好的示例:
```bash
npm install
npm test
npm run build
```
```

**说明**:
- 包含注释说明每个命令的作用
- 命令之间空行分隔
- 使用实际可执行的命令

### 输出示例

**真实性**:
```markdown
✅ 好的示例:
```text
$ npm test

> project@1.0.0 test
> jest

 PASS  src/utils.test.js
  ✓ should format date correctly (3ms)
  ✓ should validate email (2ms)

Test Suites: 1 passed, 1 total
Tests:       2 passed, 2 total
```

❌ 不好的示例:
```text
测试通过
```
```

**说明**:
- 使用真实的输出
- 包含关键信息
- 保持格式完整

### 配置示例

**注释说明**:
```markdown
✅ 好的示例:
```json
{
  "name": "project-name",        // 项目名称
  "version": "1.0.0",            // 当前版本
  "scripts": {
    "build": "webpack",          // 构建命令
    "test": "jest"               // 测试命令
  }
}
```

❌ 不好的示例:
```json
{
  "name": "project-name",
  "version": "1.0.0",
  "scripts": {
    "build": "webpack",
    "test": "jest"
  }
}
```
```

## 错误处理

### 常见错误章节

如果有常见错误，添加专门章节：

```markdown
## Troubleshooting

### 错误: [错误信息]

**症状**: 描述错误现象

**原因**: 解释错误原因

**解决方法**:
1. 步骤 1
2. 步骤 2

**验证**: 如何确认问题已解决

---

### 错误: [错误信息]

[同样的结构]
```

### 内联错误处理

在步骤中包含错误处理：

```markdown
3. **运行构建命令**

   ```bash
   npm run build
   ```

   **如果遇到错误**:
   - `Error: Module not found` → 运行 `npm install`
   - `Error: Permission denied` → 使用 `sudo` 或检查文件权限
```
