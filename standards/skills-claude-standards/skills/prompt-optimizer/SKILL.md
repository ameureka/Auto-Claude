# Skill: prompt-optimizer

将非结构化的自然语言提示词转换为结构化的 R.C.T.C.D 格式，提升 AI 交互效率和输出质量。

## 元信息

| 属性 | 值 |
|------|-----|
| 版本 | 1.1 |
| 作者 | Auto-Claude |
| 触发命令 | `/prompt-optimizer` |
| 适用场景 | 编程/开发任务提示词优化 |
| FPF 审查 | ✅ 通过 (2024-12-31) |

## R.C.T.C.D 模型

| 要素 | 英文 | 说明 | 示例 |
|------|------|------|------|
| **R** | Role | AI 应扮演的角色 | 资深 React 开发工程师 |
| **C** | Context | 项目背景和技术栈 | Next.js 14 项目，使用 TypeScript |
| **T** | Task | 具体任务和子任务 | 实现用户登录功能 |
| **C** | Constraints | 约束条件和限制 | 使用现有 UI 组件库 |
| **D** | Deliverables | 可验证的交付物 | 登录页面组件、API 路由、测试用例 |

## 使用方法

```bash
/prompt-optimizer <原始提示词>
```

### 示例

```bash
/prompt-optimizer 帮我写个登录功能
```

## 工作流程

```
┌─────────────────────────────────────────────────────────┐
│                  prompt-optimizer                        │
├─────────────────────────────────────────────────────────┤
│                                                          │
│  Phase 0: Validate (输入验证)                            │
│  ├── 检查输入长度 (3-2000 字符)                          │
│  ├── 检查是否包含任务意图                                │
│  └── 失败时请求澄清                                      │
│           │                                              │
│           ▼                                              │
│  Phase 1: Parse (解析)                                   │
│  ├── 提取关键词和意图                                    │
│  ├── 识别技术栈线索                                      │
│  └── 检测隐含约束                                        │
│           │                                              │
│           ▼                                              │
│  Phase 2: Transform (转换)                               │
│  ├── Role: 根据推断表确定角色                            │
│  ├── Context: 提取项目/技术背景                          │
│  ├── Task: 分解为主任务+子任务                           │
│  ├── Constraints: 建议模式 [建议]                        │
│  └── Deliverables: 定义可验证交付物                      │
│           │                                              │
│           ▼                                              │
│  Phase 3: Output (输出)                                  │
│  ├── 生成结构化提示词                                    │
│  └── 展示转换说明                                        │
│           │                                              │
│           ▼                                              │
│  Phase 4: Confirm (确认)                                 │
│  ├── 用户确认或调整                                      │
│  └── 支持迭代优化                                        │
│                                                          │
└─────────────────────────────────────────────────────────┘
```

## 输入限制

| 限制项 | 值 | 说明 |
|--------|-----|------|
| 最小长度 | 3 字符 | 过短无法推断意图 |
| 最大长度 | 2000 字符 | 超长需分拆处理 |
| 极短输入 | < 10 字符 | 触发澄清流程 |

## 适用范围

| 类型 | 支持 | 说明 |
|------|------|------|
| 编程/开发任务 | ✅ | 主要适用场景 |
| 中文输入 | ✅ | 完全支持 |
| 英文输入 | ✅ | 完全支持 |
| 非技术任务 | ❌ | 写作、翻译等不适用 |
| 纯问答请求 | ❌ | "什么是 React?" 不适用 |

## Role 推断表

| 关键词 | 推断角色 |
|--------|----------|
| 前端、React、Vue、CSS | 资深前端开发工程师 |
| 后端、API、数据库、Python | 资深后端开发工程师 |
| 全栈、登录、认证 | 资深全栈开发工程师 |
| 测试、QA、自动化 | 资深测试工程师 |
| 部署、CI/CD、Docker | 资深 DevOps 工程师 |
| 架构、重构、设计 | 资深软件架构师 |
| 安全、加密、认证 | 资深安全工程师 |
| 数据、分析、ML | 资深数据工程师 |
| 默认 | 资深软件开发工程师 |

## Context 提取规则

1. **技术栈检测**: 从关键词推断 (React, Python, Node.js 等)
2. **项目类型推断**: Web应用、CLI工具、API服务等
3. **环境信息**: 开发/生产、本地/云端
4. **现有代码**: 是新建还是修改现有功能

## Constraints 自动建议

以下约束会以 `[建议]` 标记自动添加，用户可选择保留或移除：

| 场景 | 建议约束 |
|------|----------|
| 前端开发 | [建议] 遵循现有代码风格和组件规范 |
| API 开发 | [建议] 保持 RESTful 设计原则 |
| 数据库操作 | [建议] 使用参数化查询防止注入 |
| 认证功能 | [建议] 遵循 OWASP 安全最佳实践 |
| 通用 | [建议] 添加必要的错误处理 |

## 示例转换

### 示例 1: 简单任务

**输入**:
```
写个按钮组件
```

**输出**:
```markdown
## Role
资深前端开发工程师

## Context
- 需要创建一个可复用的按钮组件
- 技术栈待确认（React/Vue/原生）

## Task
**主任务**: 创建按钮组件

**子任务**:
1. 定义按钮的 props 接口
2. 实现按钮样式（默认、hover、disabled）
3. 添加点击事件处理

## Constraints
- [建议] 遵循现有代码风格和组件规范
- [建议] 支持多种尺寸和颜色变体

## Deliverables
- [ ] Button 组件文件
- [ ] 组件样式文件
- [ ] 使用示例
```

**输入**:
```
用 React 写一个支持拖拽排序的列表

资深前端开发工程师，精通 React 和拖拽交互实现

## Constraints
- [建议] 使用成熟的拖拽库而非原生实现
- [建议] 确保移动端触摸支持

**输入**:
```

## Role
资深软件架构师，精通认证系统设计和安全最佳实践

## Context

- 需要支持两种认证方式：OAuth 和 API Key

**子任务**:
1. 分析现有认证模块架构
2. 设计统一的认证接口抽象

## Constraints
- [建议] 遵循 OWASP 安全最佳实践
- [建议] 保持向后兼容，支持渐进式迁移
- [建议] API Key 需要安全存储（哈希）
- [建议] OAuth token 需要安全的刷新机制

## Deliverables
- [ ] 认证接口抽象层
- [ ] OAuth 认证提供者实现
- [ ] API Key 认证提供者实现
- [ ] 认证策略选择器
- [ ] 更新后的 API 端点

## 错误处理

### 输入为空
```
❌ 输入不能为空

请提供需要优化的提示词，例如：
/prompt-optimizer 帮我写个用户登录功能
```

### 输入过短 (< 3 字符)
```
❌ 输入过短，无法推断任务意图

请提供更详细的描述，至少包含：
- 要做什么（动作）
- 做什么东西（对象）
```

### 输入过长 (> 2000 字符)
```
❌ 输入超过 2000 字符限制

建议：
1. 精简描述，保留核心需求
2. 将大任务拆分为多个小任务
3. 分别优化每个小任务的提示词
```

### 极短输入澄清 (< 10 字符)
```
⚠️ 输入信息较少，需要澄清

检测到的意图: [推断的意图]

请补充以下信息：
1. 使用什么技术栈？
2. 是新建还是修改现有功能？
3. 有什么特殊要求？
```

### 非编程任务
```
⚠️ 检测到非编程任务

prompt-optimizer 专为编程/开发任务设计。

您的输入看起来是: [检测到的类型]

如果这确实是编程任务，请补充技术相关的描述。
```
